# /mission-init

Brief: $ARGUMENTS
(Empty → take the brief the user just pasted and write it word for word into `.mission/brief.md`. Do not write customer addresses/names — replace them with short codes.)

## 1. Create the skeleton

```bash
node "$MISSION_KIT/mission.mjs" init --brief "<tệp yêu cầu>" --name "<tên app>"
```

## 2. Read what the app ALREADY has (do not redo it, do not overwrite it)

- `CLAUDE.md`, `AGENTS.md`, README — write the mandatory rules into `plan.md`.
- `.claude/settings.json` — the app's own hooks (guard, build after edit, privacy…). They keep running alongside the kit; do **not** declare the same job again in `checks.onEdit` (avoids building twice).
- `.claude/skills/`, `.claude/agents/` — the app's own skills for review/checking/deploy. Fill them into `appSkills` so the kit uses them instead of the generic skills:
  ```json
  "appSkills": { "review": "ba-chuyen-gia", "verify": "verify", "deploy": "ship", "drawings": "doc-ban-ve",
                 "privacy": "privacy-auditor", "accessTest": "access-test", "migration": "migration",
                 "newSample": "them-mau", "handoff": "gui-chatgpt" }
  ```
- Existing check scripts (`tools/`, `scripts/`, `package.json` scripts, `ship.sh`…) — use them as `checks.full`.
- An existing privacy block list (e.g. `.claude/redaction-denylist.txt`) — point `privacy.denylistFiles` at it (one source of truth).
- Existing privacy hooks/agents (`privacy-guard`, `scan-client-leak`, `privacy-auditor`): read them to fill the `privacy` block correctly (sample folders, file extensions that must never be committed, names of secret server-side data); the app's hooks keep running, the kit only adds one more layer. If the app has its own privacy review agent → `appSkills.privacy`.
- `deny` permissions in `.claude/settings.json` (Read `.env`, private folders, `INTERNAL`/`Payroll`…) → move that intent into `readGuard` (the kit understands shell commands too, not only the Read tool).
- File/line lock hooks, slow-test reminder hooks, a send-to-ChatGPT workflow (a hook that checks what is sent, a packaging skill) → fill `protect.lockedText`, `checks.remind`, `handoff` (table below). If the old workflow copied to Dropbox → **do not copy the Dropbox path**: set `handoff.exchangeDir` to an outbox inside the app (e.g. `docs/reviews/outbox`); sending to/receiving from ChatGPT is now done with Claude's browser (see `/mission-handoff`).
- **Do not declare again what the app's hooks already do** (two hooks doing the same job = Claude gets two reminders/two blocks): if the app already has a slow-test reminder hook, leave `checks.remind` empty; if it already has `scan-client-leak`, leave `privacy.clientCode` empty. Only fill in rules the app does NOT have yet (e.g. `readGuard`, commit message checks).
- The app's own skills for permissions, migration, new sample sets, sending to ChatGPT (e.g. `access-test`, `migration`, `them-mau`, `gui-chatgpt`) → `appSkills.accessTest`, `appSkills.migration`, `appSkills.newSample`, `appSkills.handoff`.
- How git is used: is there a remote, are commits made straight to `main` → choose `git.mode`. No GitHub repo yet, or the app already has auto-push turned on (`git config --get core.hooksPath`, `tools/git-hooks/post-commit`) → write it into `plan.md`; to back up to GitHub, use the `mission-github` skill (only if the project owner agrees).

**You must finish all of step 2 before filling in step 3.** When you report `/mission-init` as done, `config.json` must not still contain template values (`index.html`, `samples/*.pdf`, `skill ship` when the app uses a different skill…) unless the app really has them.

## 3. Fill in `.mission/config.json`

| Key | What to fill in |
| --- | --- |
| `git.mode` | `local-main` (default: commit straight to the main branch on this computer, push must ask — unless the project owner has turned on auto-push via `mission-github`) or `branch-pr` (separate branch + PR) |
| `deliverables` | The real outputs (e.g. build files), not source files. `done` checks that they exist and are newer than the source. |
| `protect.deny` | Never edit: original data, existing samples (`samples/**` — **only add this after the project owner has copied the samples in**). Do **not** put files generated by a build/script here: `deny` also blocks the build command that writes that file. Generated files → `protect.ask` (or let the app's own hook handle them). |
| `protect.ask` | Needs confirmation: deploy configuration, rules, expected results, CI. |
| `bash.ask` | Regex for project-specific commands that need an extra ask. Commands containing `deploy/publish/release/ship` and exactly `ship.deployCmd`/`previewCmd` **already ask on their own** — no need to declare them again. |
| `units` | How the work is split: features (`list`), sample projects, rules. `units[].gates` = a list of gates specific to that group (e.g. samples only need G3, G7) to save effort. |
| `gates` + `independentGates` | Default G1–G8 (see `mission-quality-gates`). |
| `checks.full` | The app's existing scripts + `web-smoke` if it is a web app. Use `$MISSION_KIT` freely — the CLI replaces the path itself and it works on Windows. |
| `lint.rules` | Secret keys, hard-coded rule thresholds… The `console-log` rule: remove it if the app uses `console.log` on purpose (hundreds of warnings are just noise). |
| `privacy` | `patterns` (regex) and `denylistFiles` — the CLI refuses to write ledger/gate entries whose content matches; a hook blocks any **commit** whose content matches. Australian-style home addresses (the kit's default; apps in other countries should add their own patterns to `patterns`) are always blocked (unless `addressCheck: "off"` — this applies to commits only). The default patterns include Australian phone numbers and `LOT n DP n`. An app with **no customer data** (a game, a public handbook) → `addressCheck: "off"` so public addresses/street names in stories are not blocked. `allowPatterns`: fake data that is allowed (e.g. street names in test samples). `sampleDirs`: folders of customer drawings/files (e.g. `["samples"]`) — file names inside them (and the address part after the job number) must not go into commits. `blockCommitExtensions`: file extensions that are never committed (e.g. `["pdf","zip"]` when the samples are customer PDFs). `blockPush: true` when the git history still has customer information that has not been cleaned. `clientCode`: `{ identifiers: [regex tên bảng/cột/khóa mật], serverMarker: "import .server-only.", serverMarkerLabel: "thêm import 'server-only'", ignoreCase: false }` (`identifiers`: regex for table/column/secret-key names; `serverMarkerLabel`: text shown, here "add import 'server-only'") — code that can reach the browser and mentions them is blocked right after the edit. `addressCheck`: `"strong"` (default for commits: only clear street suffixes such as Street, Road, Avenue, Crescent), `"all"` (also Close, Way, Drive, View…), `"off"`. The block message points to `file:line`; test data with fake street names → add to `allowPatterns`. |
| `readGuard` | By default it already blocks reading secret files (`.env`, `.dev.vars`, keys, `~/.ssh`, `~/.wrangler`…) and **asks** when reading Desktop/Documents/Pictures/Videos/Music/OneDrive/Dropbox. `extraPrivateDirs`: **adds** extra private folders (ask before reading); `privateDirs` **replaces** the whole default list — usually not used. `denyDirs`: folders that are never read (e.g. the other apps in the apps folder — `MISSION_APPS_ROOT`). `extraSecrets`: globs inside the app that must not be read (e.g. `"reference/**"`, `"**/*Payroll*"`). `allowDirs`: exceptions. `outside: "ask"` if you also want to ask when reading anywhere outside the app. |
| `protect.lockedText` | `[{ "glob": "tests/run.js", "text": "<string that must stay unchanged>", "why": "fingerprint of a locked rule", "mode": "untouchable" }]` — the file can still be edited, but not that string. `mode: "untouchable"`: blocks any edit whose old text touches the string (including turning that line into a comment) — use it for fingerprints/hashes. |
| `checks.remind` | Checks too slow to run automatically (need desktop software, long browser runs): `[{ "glob": "tools/slow/**/build.py", "name": "Slow", "message": "run_slow.ps1", "skill": "slow-test" }]` — when a matching file is edited, Claude is reminded to run it before reporting done. |
| `handoff` | Only when the app sends work to ChatGPT for review: `exchangeDir` = an outbox **inside the app**, as a relative path (e.g. `"docs/reviews/outbox"`; do not use Dropbox — ChatGPT receives it through Claude's browser), `verdictGlob` (e.g. `"**/*CHATGPT_VERDICT*"`), `verdictSourceLine` (regex for the source line — **required** when `verdictGlob` is set), `blockNames`, `blockExtensions` (declaring it **replaces** the whole default list xlsx/xls/xlsm/pdf/zip — remember to keep them), `blockAmounts` + `syntheticAmountsFile` (apps with real money amounts). |
| `samples` | Only for apps that read drawings: `dir`, `readCmd`, `overlayCmd`, `reviewCmd`, `checkCmds`, `expectedFile`, `historyFile` for `/mission-new-sample`. Add `expectedFile` to `protect.ask` (only the project owner approves expected results). |
| `stopGate` | `watch` = leave empty (default: watch every file git tracks) or limit it to the real source folders; `mode` = `remind` (default, only reminds) or `block`. |
| `threeExperts.areas` | Three areas for the `ba-chuyen-gia` skill: each area has `name`, `files` (glob), `focus` (what to look for), `commands` (check commands). Not filled → defaults: core/logic · data and edge cases · user/interface. |
| `tidy` | For `/mission-tidy`. `include`: globs of the real source code (e.g. `src/**/*.js`), not the build output. **`sharedScope`**: if the build joins several files into one (e.g. concatenates `src/js/*.js`) or the page loads several non-module `<script>` tags → declare one entry per group, e.g. `[["src/js/*.js"]]`; then the kit catches functions/variables with the same name across files (the one loaded later overrides the earlier one). App uses `import/export` → leave it empty. Default thresholds: file 400 lines, function 80 lines, repeated block 8 lines. `onEdit` (default `true`): the after-edit hook warns about duplication involving the file just edited; a very large app where the hook feels slow → `false`. |
| `ship` | `checkCmd` (check, do not publish), `previewCmd` (preview version — leave empty if the app has none), `deployCmd` (**the live site**), `siteUrl`, `lockChecks` (URL + expected status code), `backupDir` (a **relative** path inside the app, default `build/backup`; no Dropbox, do not copy absolute paths from old notes), `backupFiles`, `tag`. Take these from the app's `CLAUDE.md`/`ship.sh`, do not guess. **Test copy / duplicate** (the brief or the project owner says «test copy» (or «bản thử»), or the folder is not where the real app lives): leave `deployCmd` and `previewCmd` empty. |
| `mainBranch` | The main branch (filled in automatically at init). Only used when opening a PR in `branch-pr` mode. |
| `review` | `defaultAgents` (default 3 = three experts; small jobs use `/mission-review <unit> quick` (or `nhanh`) = 1), `maxRounds` (default 3). |

Templates: `$MISSION_KIT/templates/config.template.json` and `$MISSION_KIT/templates/examples/`.

**Another computer / fresh clone:** the kit's hooks live in `.claude/settings.local.json` and the copy of the kit is not committed, so on a new computer you must run `node install.mjs --lang en --project "<app folder>"` again. `.mission/state/` and `manifest.json` are not committed either, so you need to run `scan` → `check --full` → `report` → commit again before `done` passes (gates already scored stay valid if their content has not changed).

## 4. Check the configuration

```bash
node "$MISSION_KIT/mission.mjs" scan
node "$MISSION_KIT/mission.mjs" lint --all --summary
node "$MISSION_KIT/mission.mjs" check --full
node "$MISSION_KIT/mission.mjs" report
```

`check --full` being red at first is normal — it is the baseline for comparison. For each red step you do not fix right away, record `ledger add --category blocker --loc "check:<step name>" --severity … --why … --fix …` so the stop hook does not keep reminding you.

## 5. Specification

Use the `mission-app-spec` skill to fill in the rest of `plan.md`.

## 5a. Feature map (keep the code tidy from the start, so no periodic tidy is needed)

Fill in the «Features» section of `.mission/LT.md`, one feature per line: `<feature> — <folder/file> — <functions/concepts it owns>`.

- **New app:** give each feature its own folder (e.g. `src/features/<name>/`); parts used by ≥2 features → one shared folder (e.g. `src/shared/`). Write this split into `HTC.md` (the «Code / naming conventions» section).
- **Existing app:** **do not move files** just to make it look nicer. Only write the map according to the current structure (which feature is in which file, which function is the owner). Re-splitting folders is the job of `/mission-tidy`, when the project owner agrees.
- Each concept (date formatting, area calculation, API calls…) has only **one** owner; other places call into it.
- The after-edit hook warns automatically: duplicate names, a function with the same name already in another file, repeated blocks, new files not yet in LT.md. The `tidy --conflicts` step in `checks.full` blocks real name conflicts at the check point. An old app that already has conflicts → `check --full` is red at that step: record `ledger add --category blocker --loc "check:tên trùng (xung đột)" …` (the step name, "duplicate names (conflict)") and then clean up with `/mission-tidy`; do not remove the check step from the config.

## 5b. The «Must not change» block in `CLAUDE.md`

`CLAUDE.md` is loaded in **every** session, even when the kit's hooks do not run (computer without Node, kit not installed, light version). So the things that must never change have to be there, not only in `HTC.md`/`plan.md`.

- Read the existing `CLAUDE.md`. If it already has a similar section (fixed rules, «never», «forbidden»…) → only propose adding the missing lines, do not rewrite it.
- Draft a `## Must not change` block of ≤ 30 lines, one checkable item per line: architecture (e.g. «rule calculation logic lives only on the server»), security boundaries (keys in environment variables, private repo), customer data (never in commits/logs), original data and expected results (only the project owner changes them), how to prove «done» (which check command must be green). Take these from the brief, the old `CLAUDE.md`/README and the config you just filled in — do not invent new rules.
- Do not copy the contents of `QUY-TRINH.md` or general instructions; only things specific to the app. Long details stay in `HTC.md`; `CLAUDE.md` keeps only one line per item.
- **Show this block to the project owner in the step 6 report and only write it into `CLAUDE.md` when the project owner agrees** (the hook also asks before writing `CLAUDE.md`). Once agreed, make the «Prohibitions» section of `HTC.md` point to that block (one source of truth).

## 5c. AI model

A new app gets its model configuration (main session `sonnet`, advisor `fable`) from `node "<kit folder>\install.mjs" --lang en --project <app folder>` — run this command if the app's `.claude/settings.json` does not yet have `model`/`advisorModel`. Values the app has set itself stay as they are. The kit's subagents already declare `model:` in their own files (opus: review; sonnet: check/snapshot; haiku: search and read), no need to copy anything more.

## 6. Report to the project owner

Short, in English: V1 scope, current state (the check baseline), which of the app's own skills will be used, assumptions, questions that need answers (gathered in one go).
